# FormosaNLU v1.2.1 Closeout Design

## 1. Purpose

Publish an immutable `v1.2.1` closeout release that repairs public metadata and
broken evidence links, synchronizes the repository and Hugging Face cards with
the completed M19 evidence, improves discoverability and citation readiness,
and adds an English paper-style technical report. The closeout must not change
any experiment, dataset row, model tensor, parser, threshold, prompt, seed, or
evaluation result.

## 2. Current Evidence and Problems

The experimental project is complete and `v1.2.0` is public. Fresh local gates
pass and release preflight reports `public_verified`. The remaining problems
are publication-layer inconsistencies:

1. All five evidence links rendered in the `v1.2.0` GitHub Release return HTTP
   404 because repository-relative links were interpreted in Release context.
2. `docs/NEXT_SESSION.md` names two reports that do not exist.
3. The README license table groups all student weights under Apache-2.0 even
   though the Phi-4-mini replication model uses MIT.
4. The current handoff still calls the released data card a pre-release draft.
5. `reports/m13_publication.json` records the initial Hugging Face commits,
   not the current card commits.
6. The public Hugging Face cards contain M15/M16 evidence but not M19; the
   model card still reports the older 23.124-hour resource total.
7. GitHub has no repository topics or homepage, and GitHub reports the license
   as `Other` because a scope note is appended to the canonical MIT text.
8. The release has no downloadable evidence assets and the project has no DOI.

## 3. Integrity Constraints

- Keep `v1.0.0`, `v1.1.0`, and `v1.2.0` immutable.
- Keep the public Dataset at exactly 3,754 rows and preserve its train SHA-256
  `c65d7209d953e144299625f6a9224b98557b2677d55258a463a2992e5acf4665`.
- Preserve the public Gemma adapter byte size `155,609,536` and SHA-256
  `f70f423814dcd47943c92c0beb8b08a4e7f65e60a44355d3dcd95bed9f0bd60a`.
- Do not publish Phi weights or adapters.
- Do not rerun M9, M15, M16, M19, generation, filtering, Colab, or robustness.
- Preserve M19's preregistered 2.5-point threshold, single-seed limitation,
  negative interpretation, and `causal_claim_allowed=false`.
- Git author and committer must remain
  `kuotunyu <61350295+kuotunyu@users.noreply.github.com>` with no
  `Co-Authored-By`; GitHub Contributors must remain exactly `kuotunyu`.
- Repository prose remains primarily Traditional Chinese (`zh-TW`); the new
  paper-style report is English to improve research reach.

## 4. Versioning Strategy

Use `v1.2.1` as a metadata/documentation patch release. It changes no released
Dataset or Model artifact, but it does change repository software, citation
metadata, documentation, public cards, and evidence packaging.

- Update `pyproject.toml` and `CITATION.cff` from software version `1.0.0` to
  `1.2.1` and update the citation release date.
- Continue describing the public Dataset and Gemma adapter as their existing
  artifact release; explicitly distinguish artifact identity from repository
  evidence/software version.
- Create a new annotated `v1.2.1` tag. Never move an older tag.
- Use a patch release rather than `v1.3.0` because no new experiment or result
  is introduced.

## 5. Repository Changes

### 5.1 Persistent closeout verifier

Add a focused `scripts.verify_closeout` gate and tests. It will verify:

- tracked local Markdown links resolve;
- release-note evidence links use absolute, tag-pinned GitHub URLs;
- the report paths named by `docs/NEXT_SESSION.md` exist;
- README and data-card model-license statements distinguish Phi MIT from the
  Apache-2.0 primary roles;
- Hugging Face card sources contain the M19 result, the 42.412-hour total, and
  the no-causal-claim limitation;
- `pyproject.toml` and `CITATION.cff` agree on `1.2.1`;
- the third-party scope notice exists outside the canonical MIT `LICENSE`.

Register this verifier in `scripts.check_gates` so future local pushes cannot
reintroduce these failures. Tests follow RED-GREEN-REFACTOR: each new check is
first demonstrated to fail against the current tree, then made green by the
minimal documentation or metadata change.

### 5.2 Documentation corrections

- Fix the two incorrect M15/M16 paths in `docs/NEXT_SESSION.md`.
- Correct README model-license wording.
- Replace the active pre-release wording in `docs/HANDOFF.md`.
- Convert the five `docs/RELEASE_NOTES_v1.2.0.md` evidence links to absolute,
  `v1.2.0`-pinned URLs and edit the existing GitHub Release body to match.
- Update release instructions and handoff records for `v1.2.1` without
  rewriting historical log entries.

### 5.3 License recognition

Restore `LICENSE` to the unmodified canonical MIT text. Move the existing scope
note verbatim into `THIRD_PARTY_NOTICES.md`, with links to the data card and
upstream licenses. This keeps the legal clarification while allowing GitHub's
license detector to identify MIT.

### 5.4 English technical report

Add a paper package under `paper/`:

- `paper/formosanlu_synth.tex`: English manuscript with abstract,
  introduction, related work, method, frozen experimental design, results,
  robustness, cross-family replication, M19 negative result, limitations,
  ethics/licensing, resource accounting, and reproducibility statement;
- `paper/references.bib`: primary-source bibliography;
- `paper/README.md`: reproducible build instructions and scope statement.

Every numeric claim must come from tracked machine-readable reports or README
verifier-backed values. No new statistical claim is allowed. If a local LaTeX
engine is available, compile and inspect the PDF; otherwise validate the source
structure and leave a documented build command for Overleaf/arXiv.

## 8. Zenodo and Citation Flow

Prepare Zenodo-compatible metadata from `CITATION.cff`, the technical report,
release notes, licenses, authorship, keywords, and public artifact URLs.

The user may need to sign in to Zenodo and authorize GitHub access. No account
creation, OAuth grant, DOI reservation, or record publication is inferred from
repository authorization. When that interaction is reached:

1. pause and provide one exact user action at a time;
2. create or connect the Zenodo record for `v1.2.1`;
3. verify the archived commit/tag and files;
4. add the minted DOI to the GitHub Release, repository About, README badge,
   and citation metadata without moving the published tag.

If Zenodo can only mint the DOI after release publication, record the DOI in a
post-release documentation commit and do not create another release solely for
that backlink.

## 9. Publication Order and Failure Handling

1. Implement and test repository changes locally.
2. Run full local gates and inspect the complete diff.
3. Update Hugging Face cards only; verify immutable artifact hashes.
4. Refresh `reports/m13_publication.json` with the new HF card commits.
5. Commit and push the final source/evidence tree.
6. Verify GitHub commit identity and sole contributor.
7. Create and push `v1.2.1`, then create the GitHub Release and attach assets.
8. Update GitHub topics/homepage and verify license recognition.
9. Run anonymous publication verification, release preflight, rendered-link
   checks, asset SHA checks, and a clean-worktree audit.
10. Proceed to Zenodo only when the user-authenticated step is available.

If an external write partially succeeds, do not overwrite data, weights, or
old tags. Record the exact remote commit/state, repair only the card, metadata,
or release entry that failed, and rerun immutable-artifact verification before
continuing.
